# Регламент разработки

Правила, обязательные для всего кода и текстов в репозитории. Прочти перед
первым PR — ревью опирается на этот документ.

## Язык

Строгое разделение: **английский — в коде, русский — для людей.**

| Где | Язык |
| --- | --- |
| Комментарии и JSDoc в коде | **английский** |
| Имена переменных, функций, типов, файлов | **английский** |
| Сообщения коммитов, названия веток | **английский** (Conventional Commits) |
| Строки в `.env` и комментарии к ним | **английский** |
| Документация (`README`, `AGENTS.md`, `docs/`, этот файл) | **русский** |
| Пользовательский интерфейс (тексты бота, PWA, писем) | **русский** |
| Логи и сообщения об ошибках для оператора | **русский** |

Смешивать в одном файле нормально: русский текст в UI-строке рядом с английским
комментарием — это ожидаемо, а не исключение.

## Комментарии

**Пишем самодокументируемый код.** Комментарий — не бесплатный: его придётся
поддерживать, и он протухает быстрее кода. Поэтому:

- **Комментируем только там, где смысл кода не очевиден.** Если из имён и
  структуры и так всё ясно — комментарий не нужен.
- **Коротко и простым языком.** Одна-две строки. Не пересказ кода, а «почему так»:
  причина, ограничение, неочевидный побочный эффект.
- **JSDoc — компактный**, одной строкой (`/** Ключ S3 для сырья события. */`).
  Многострочный JSDoc с `@param`/`@returns` — только если сигнатура правда
  требует пояснений; типы и так видны из TypeScript, дублировать их не надо.
- **Не комментируем очевидное.** `// increment counter` над `counter++` — мусор.
- **Не оставляем закомментированный код.** Для истории есть git.

Хороший комментарий отвечает на «почему», плохой — пересказывает «что».

```ts
// Плохо: пересказ кода
// Increment the retry counter
retries++

// Хорошо: неочевидная причина
// Frigate re-sends `end` for the same event; skip so we don't double-deliver.
if (seen.has(event.id)) return
```

### `.env`-файлы

Комментарии в `.env`/`.env.*.example` — на английском, **очень короткие и
максимально простые**: их читает человек, впервые разворачивающий проект, а не
разработчик. Одна строка на переменную, без терминологии, где можно без неё.
Помечай, что обязательно к заполнению, а что имеет рабочий дефолт.

## Стиль кода

- Biome: одинарные кавычки, **без точек с запятой**, отступ 2 пробела.
  Импорты сортируются автоматически.
- `noExplicitAny` и `noForEach` выключены — `any` допустим там, где иначе никак.
- `process.env` читаем **только** в `config.ts` сервиса, через `env`-хелпер.
- Перед завершением задачи — `bun run green` (typecheck + тесты + biome по
  всему репо).

Подробнее об архитектурных конвенциях (Regulator, Controller → Action,
логирование, единый `.env`) — в [AGENTS.md](AGENTS.md).

## Коммиты и релизы

- **Conventional Commits** — иначе упадёт commitlint:
  `fix:` → patch, `feat:` → minor, `feat!:` / `BREAKING CHANGE` → major.
  Типы: `agents`, `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`,
  `refactor`, `revert`, `style`, `test`.
  Регистр заголовка не проверяется — пиши как читается (`fix: Biome upgrade`).
  Проверить сообщение локально: `echo 'fix: ...' | bunx commitlint`.
- К изменению, влияющему на пользователей, добавляй changeset: `bunx changeset`.
- Версионирование и сборка образов — автоматические, по мержу в `master`.
  Детали — в [docs/operations.md](docs/operations.md).
