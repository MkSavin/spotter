# Тестирование на настоящем NVR — TODO-спека

Заменить самодельный впрыск событий на настоящий Frigate, который сам их порождает и сам публикует в MQTT. Цель — покрыть участок, который сейчас не покрыт ничем и который в сентябре 2026 молчал двое суток.

## Что не покрыто сегодня

`test_delivery` и `test_media` публикуют в `spotter.event.test_seed` — **минуя MQTT**. Адаптер получает не то, что шлёт Frigate, а то, что мы считаем правильным.

В smoke NVR — HTTP-заглушка на Bun ([`.e2e/smoke/nvr.ts`](../.e2e/smoke/nvr.ts)). Она отвечает на `/api/config` и отдаёт байты, но **не публикует в MQTT ничего**. Mosquitto в стенде поднят, и по нему не проходит ни одного события.

То есть непроверенными остаются: подписка на топики, разбор реального payload `frigate/events`, `frigate/reviews` и вывод `severity`, поведение при переподключении к брокеру. Ровно тот участок, где случился сбой.

## Механизм: детектор по ZMQ

У Frigate нет хука «создать событие», и форк ради этого — плохая цена. Но есть штатный плагин-детектор [`zmq_ipc`](https://github.com/blakeblackshear/frigate/blob/v0.17.2/frigate/detectors/plugins/zmq_ipc.py), который не считает сам, а спрашивает результат по сокету:

```
Frigate  → [ header_json, tensor_bytes ]   кадр
детектор → [20, 6] float32                 что «найдено» в кадре
```

Строка результата: `[class_id, score, y_min, x_min, y_max, x_max]`, координаты нормированы 0..1. Пустые строки — нули.

Мы подменяем **только зрение**. Всё после него настоящее: Frigate ведёт трекинг, решает, что это событие, пишет запись, считает `severity` и публикует `frigate/events` и `frigate/reviews` сам.

Контракт стабильнее HTTP API — это интерфейс плагина, а не эндпоинт. Но он не вечен: закрепить версию образа Frigate в стенде и проверять при обновлении.

Протокол проверен вживую: handshake отвечает `{"model_available":true,"model_loaded":true}`, инференс возвращает ровно 480 байт (20 × 6 × float32), Frigate разбирает их как детекции.

`endpoint` в конфиге детектора — обычная строка, уходящая в `socket.connect`, поэтому `tcp://spotter-probe:5555` работает наравне с `ipc://`. Это и позволяет держать probe отдельным контейнером, а не сайдкаром в одном namespace с Frigate.

Ещё две детали из исходника плагина, обе неочевидные:

**Файл модели не нужен, но путь обязателен.** Плагин берёт `os.path.basename(model.path)` **до** всякого обмена, поэтому без пути падает на старте. При этом сам файл не читается: `compute_model_hash` на несуществующем пути просто хеширует `b"unknown"`. Мы отвечаем «модель готова», байты не передаются, весов скачивать не надо — в конфиге достаточно строки.

**Таймаут по умолчанию 200 мс.** На каждом просроченном ответе Frigate пересоздаёт сокет и заново гоняет handshake. На загруженной машине это происходит постоянно, поэтому в стенде `request_timeout_ms: 5000`.

### Ограничение: zeromq не работает под Bun

`zeromq@6` (нативный аддон) под Bun 1.4 падает уже на `bind`:

```
panic(main thread): unsupported uv function: uv_async_init
```

Под Node тот же код работает. Это [известный пробел](https://github.com/oven-sh/bun/issues/18546) в поддержке libuv, не наша ошибка — и он упирается в правило «рантайм только Bun» из `AGENTS.md`.

Варианты, в порядке предпочтения:

1. **Probe как отдельный контейнер на Node.** Он и так отдельный образ, внутрь монорепа-рантайма не лезет. Правило про Bun остаётся в силе для сервисов; тестовый инструмент — не сервис. Дёшево и сразу работает.
2. **Свой ZMTP поверх `Bun.listen`.** ZMTP 3.1 REP — документированный протокол: greeting, READY-handshake, length-prefixed фреймы. Реализуемо (нужен только REP-сокет с одним пиром), но это несколько сотен строк и свой источник багов ради тестового стенда.
3. **Дождаться поддержки libuv в Bun.** Срока нет.

**Выбран Rust.** Для него есть чистая реализация ZMQ без C-зависимости, поэтому финальный образ — статический бинарь на голом alpine: **9.65 МБ** против ~130 МБ на Node, и второй JS-рантайм рядом с Bun не появляется. Сборка целиком в Docker, на машины ничего не ставится. Подробности — в [`apps/probe/AGENTS.md`](../apps/probe/AGENTS.md).

## Состав

Новый сервис `spotter-probe`: ZMQ REP-сокет для Frigate плюс маленький HTTP-API для нас.

```
POST /detect  { camera, label, score, box?, frames? }   → выдавать детекцию N кадров
POST /clear                                             → снова пусто
GET  /health
```

По умолчанию отвечает нулями, то есть «в кадре ничего». Команда включает детекцию на несколько кадров — Frigate видит объект, ведёт его и закрывает событие.

Источник видео: `go2rtc` с зацикленным файлом или синтетическим потоком. Настоящая камера не нужна, нужен стабильный RTSP.

### Где поднимать

**В production compose — за профилем**, по образцу `pwa`/`email`:

```yaml
spotter-probe:
  profiles: [probe]
```

Это даёт то, чего сейчас нет: проверку живого узла тем же способом, что и в CI. Выключен по умолчанию — на боевом узле фиктивный детектор не должен существовать иначе как по явному запросу.

**Важно:** `probe` подменяет детектор Frigate, поэтому боевая детекция на это время выключается. В `/status` активный probe обязан быть виден красной строкой — иначе повторится сентябрь, только по нашей вине.

## Одна команда вместо двух

`test_delivery` и `test_media` уходят. Вместо них `/test`:

```
/test                    → человек на первой камере, дефолтный сценарий
/test <камера> <объект>  → конкретнее
```

Команда шлёт в `spotter-probe`, дальше всё делает Frigate. Проверяется весь путь целиком, включая MQTT.

`spotter.event.test_seed` и `eventTestController` удаляются вместе со стримом из `UP_STREAMS` forwarder'а.

Разница принципиальная: сегодня тест проверяет **наше представление** о событии, после — **реальное поведение** NVR.

## Telegram: как замкнуть end-to-end

Единственный кусок, который в smoke сейчас вырезан целиком: `spotter-telegram` в стенде отсутствует, потому что grammY с голым токеном пошёл бы в `api.telegram.org` по-настоящему.

Три варианта, от дешёвого к честному.

### 1. Локальный фейк Bot API (`apiRoot`)

grammY принимает [`apiRoot`](https://grammy.dev/ref/core/apiclientoptions#apiroot). Направляем на контейнер-заглушку, которая отвечает по схеме Bot API и **записывает** вызовы. Тест утверждает: «пришёл `sendPhoto` на такой-то чат с таким-то caption».

Дёшево, детерминированно, работает в CI без секретов. Не проверяет, что Telegram примет наш HTML и наши медиа.

### 2. Тестовое окружение Telegram (`environment: "test"`)

У Telegram есть **настоящая отдельная инфраструктура** для ботов, и grammY поддерживает её флагом `environment: "test"` — отдельные аккаунты, отдельный BotFather, отдельный токен, ничего общего с боевыми чатами.

Это честный end-to-end: реальный разбор HTML, реальная загрузка видео, реальные ограничения на размер. Требует секрета в CI и отдельного аккаунта; лимиты там строже боевых, так что для частых прогонов не годится.

### 3. Оба, на разных уровнях

Рекомендую: **(1) в smoke на каждом прогоне, (2) отдельным набором вручную или по расписанию** — перед релизом и при изменениях рендера.

`apiRoot` в конфиге перестаёт быть «ручкой ради теста»: это то, что нужно и для локального Bot API server, и для тестового окружения Telegram. Прежнее решение не добавлять его стоит пересмотреть.

## Цена

Frigate ~500 МБ и около минуты на старт; smoke заметно тяжелеет — скорее отдельный набор, чем расширение текущего. Плюс зависимость от версии Frigate в двух местах: протокол детектора и формат `frigate/events`.

Полезно ровно потому, что вторая зависимость — не наша выдумка, а то, на чём мы и так стоим. Сейчас она не проверяется никак.
