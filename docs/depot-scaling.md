# Масштабирование depot — TODO-спека

> **Статус: план, не реализация.** Ничего из описанного ниже пока не сделано.
> Документ фиксирует, что уже готово, что придётся дописать и какие развилки
> решены осознанно, чтобы не переоткрывать их заново.

Depot — самый требовательный сервис: ffmpeg и транскод видео. Цель — уметь
раскладывать его по нескольким машинам и добавлять мощности под нагрузку.

## Что уже работает

Depot — **единственный сервис без состояния**: ни БД, ни томов, ни
`DATABASE_PATH`. Единственное обращение к диску — `mkdtemp` под конкретный файл
([temp.ts](../apps/depot/src/fs/temp.ts)), который удаляется сразу после.

Из этого следует главное: **горизонтальное масштабирование уже работает**.
В [production.ingest.yml](../.deployment/compose/production.ingest.yml) два
depot с разными `REDIS_CLIENT_ID` читают одну consumer-группу, и Redis
раздаёт сообщения между ними. Третий на другой машине — это ещё один контейнер
с другим `REDIS_CLIENT_ID` и доступом к Redis и S3.

Три свойства, которые это обеспечивают, менять нельзя:

- **По шине ходят S3-ключи, не байты.** Depot не знает про NVR и его креды, поэтому
  физическое расположение узла безразлично.
- **Отвал узла обрабатывается сам.** Reaper перезабирает зависшие записи
  (`XPENDING IDLE` → `XCLAIM`): умершая посреди транскода машина не теряет работу.
- **Полосы уже разделены.** `DEPOT_LANE` (`all` / `snapshots` / `clips`) — готовый
  рычаг специализации: быстрые фото и долгое видео не мешают друг другу.

## Развилка: как сделать «резервные» depot

Требование — временные узлы включаются только когда основные забиты, и не
участвуют в обычной работе.

**Внутри одной consumer-группы это невозможно.** `XREADGROUP` раздаёт записи
всем участникам без приоритетов: подключившийся резерв немедленно начнёт
разбирать очередь наравне с основными. Приоритет придётся строить снаружи.

### Решение: отдельная группа + отложенное чтение

Резервные depot читают **тот же стрим другой consumer-группой**
(`spotter-depot-surge`) и берут запись, только если она провисела в основной
группе дольше порога. Тогда:

- при свободных основных резерв не получает ничего — записи разбираются раньше порога;
- при затыке резерв подхватывает то, до чего у основных не доходят руки;
- обе группы независимо подтверждают свои записи, дублирования нет.

Порог задаётся тем же механизмом, что уже работает: чтение `XPENDING` основной
группы перед забором. Это надстройка над `RedisRegulator`, а не его переделка.

## Что решено осознанно

**Автоскейл только для `clips`.** Образ depot — 597 МБ (ffmpeg с зависимостями,
не наш код). Поднимать инстанс ради снапшота, который обрабатывается за 16 мс,
бессмысленно. Окупается только на видео и таймлапсах.

**Приоритет — не внутри группы.** См. развилку выше: `XREADGROUP` не умеет
приоритетов, и попытка изобразить их внутри одной группы даст резерв,
работающий всегда.

**Depot остаётся stateless.** Это то, что делает всю затею возможной. Любая
попытка завести ему БД или том — повод остановиться и передумать.

## Чего в спеке намеренно нет

- **Оркестратор.** Docker Swarm, Nomad, k8s — выбор развёртывания, не кода.
  Всё перечисленное выше от него не зависит.
- **Автоскейл снапшотов.** См. выше: не окупается.
- **Шардирование по камерам.** Consumer group уже балансирует; привязка камеры
  к узлу лишит нас перезахвата при отвале и ничего не даст взамен.
