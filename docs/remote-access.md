# Ограниченный доступ к ingest-узлу

Как открыть агенту (или подрядчику) доступ к продовому ingest-узлу для разбора инцидента, не отдавая узел целиком.

Записано на будущее. Предпочтительный путь — не открывать доступ вовсе, а собирать диагностический срез командой на узле и приносить его файлом: узел не смотрит наружу, секреты не уезжают, чужих команд на проде нет.

## Что именно защищаем

На ingest лежат самые чувствительные данные системы: `FRIGATE_*` — пароли от камер (по замыслу они не покидают этот узел), `S3_*` — ключи бакета, `REDIS_REMOTE_URL` — адрес облачного Redis через туннель. Поэтому доступ даётся только на чтение, а `.env` не отдаётся вовсе.

## Правила

**Отдельный пользователь, не root, вне группы `docker`.** Членство в `docker` равносильно root на хосте: контейнер с `-v /:/host` читает и пишет что угодно. Вместо группы — точечный `sudoers` со списком разрешённых команд.

**Только чтение.** `logs`, `ps`, `inspect`, `spotter doctor`. Никаких `up`, `down`, `restart`, `exec`, никакого `redis-cli` с записью. Нужен перезапуск — его делает владелец узла руками.

**`.env` недоступен.** `chmod 600`, владелец — не тот пользователь, которому дан доступ. Какие переменные заданы, видно из `spotter doctor` и `docker inspect`, а их значения для разбора не нужны.

**Ключ ограничен и временный.** Отдельный SSH-ключ с `from=` по IP, отзывается одной строкой. Удаляется в тот же день, когда разбор закончен.

## sudoers

`/etc/sudoers.d/spotter-ro`, режим `0440`, проверить `visudo -c` до выхода из сессии:

```
Cmnd_Alias SPOTTER_RO = /usr/bin/docker compose -f /opt/spotter/.deployment/compose/production.ingest.yml logs *, \
                        /usr/bin/docker compose -f /opt/spotter/.deployment/compose/production.ingest.yml ps *, \
                        /usr/bin/docker inspect *

spotter-ro ALL=(root) NOPASSWD: SPOTTER_RO
```

Пути к `docker` и compose-файлу — под конкретный узел. Шаблоны в `sudoers` не рекурсивны, но и не строги: список стоит держать коротким и пересматривать при каждом открытии доступа.

## authorized_keys

```
from="203.0.113.7",no-agent-forwarding,no-port-forwarding,no-x11-forwarding,no-pty ssh-ed25519 AAAA... spotter-ro-2026-09
```

`no-port-forwarding` здесь существенно: без него ключ пробрасывает туннель к `local-redis` и к камерам в локальной сети, и все остальные ограничения теряют смысл.

## Закрыть доступ

```bash
sudo rm /etc/sudoers.d/spotter-ro
sudo userdel -r spotter-ro
```

Если за время доступа `.env` всё же читался — ротировать `FRIGATE_AUTH_SECRET`, ключи S3 и пересоздать туннель.
