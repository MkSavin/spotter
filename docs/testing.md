# Как проверить, что всё работает

Три уровня: unit, стенд с настоящим NVR, живой узел. Каждый отвечает на свой вопрос, и ни один не заменяет остальные.

## Зачем это появилось

1 сентября 2026 Frigate потерял сеть до брокера и **60 часов не публиковал ни одного события**. При этом: адаптер подключён и шлёт heartbeat, NVR отвечает по HTTP и показывает видео, команды `/test_delivery` и `/test_media` проходят успешно. С участка украли вещи, оповещения не было.

Обе тестовые команды писали прямо в `spotter.event.test_seed`, **минуя MQTT**. Они проверяли наше представление о событии — не поведение NVR. Участок между NVR и адаптером не проверяло ничто, и именно он лежал.

## Уровень 1: unit

```sh
bun test
```

712 тестов, десять секунд. Контроллеры, действия, схемы, регуляторы. Ничего не поднимает.

## Уровень 2: стенд с настоящим NVR

```sh
bun run nvr:source     # синтетическое видео, один раз
bun run nvr:build      # образы адаптера, домена и бота
bun run test:nvr       # ~200 секунд
```

Поднимает девять контейнеров, включая **настоящий Frigate 0.17.2**, и прогоняет всю цепочку. Подробности — в [`.e2e/nvr/README.md`](../.e2e/nvr/README.md).

Ключевая идея: **мы подменяем только зрение NVR**. Дальше всё настоящее — Frigate сам ведёт трекинг, пишет клип, считает `severity` и публикует событие в MQTT.

```
POST /detect ──► spotter-probe ──► детектор Frigate ──► трекер ──► запись
                                                                     │
      spotter.event ◄── адаптер ◄── frigate/events (MQTT) ◄──────────┘
```

Без docker или без образов набор **пропускается**, а не падает.

## Уровень 3: живой узел

Команда `/test` в боте делает то же самое на боевой машине. Но требует подготовки — см. ниже, это не кнопка на каждый день.

---

# Команда `/test`

```
/test                    → человек на первой камере
/test front              → на конкретной камере
/test front car          → и конкретный объект
```

## Как она работает

```
/test ──► spotter.probe.request.<source> ──► адаптер ──► HTTP ──► probe
                                                │
                            spotter.probe.result│  (ответ всегда)
                                                ▼
                                            сообщение в чат
```

Бот **не знает про probe** — он публикует запрос в шину, а как заставить свой NVR что-то увидеть, решает адаптер. Тот же принцип, что у `notifications.suspend`.

Ответ приходит **всегда**, включая отказ с причиной. Это важнее, чем кажется: `/test`, который молчит, неотличим от сбоя, который он ищет.

## Что нужно, чтобы она заработала

**Два условия, оба обязательны.**

### 1. Поднять probe

```sh
./spotter up --probe
```

Профиль выключен по умолчанию и **не запоминается** в `SPOTTER_PROFILES` — в отличие от `--pwa`/`--email`. Забыть фронтенд досадно; забыть probe — оставить участок без наблюдения.

CLI предупредит при запуске, а `/status` будет гореть красной строкой всё время, пока probe настроен.

### 2. Переключить детектор в конфиге Frigate

Frigate спрашивает «что в кадре» у того, кто указан в его собственном `config.yml`. Пока там настоящий детектор, probe никто не спросит.

```yaml
detectors:
  probe:
    type: zmq
    endpoint: tcp://spotter-probe:5555
    # 200 мс по умолчанию рвут сокет на любой заминке
    request_timeout_ms: 5000

model:
  # Файла может не быть: probe отвечает «модель готова», а Frigate хеширует
  # несуществующий путь как unknown. Но сам путь обязателен — плагин берёт
  # от него basename ещё до первого обмена.
  path: /config/probe.model
  width: 320
  height: 320
  labelmap:
    0: person
    1: car
```

Frigate должен быть в сети брокера (`spotter-mqtt`), иначе имя `spotter-probe` не резолвится — та же ошибка, что стоила сентябрьского простоя.

**Это перезапуск Frigate и выключение настоящей детекции.** Поэтому шаг не автоматизирован: команда в боте, молча снимающая наблюдение с участка, — плохая идея.

### После проверки

```sh
./spotter up          # без --probe
```

и вернуть детектор в `config.yml` Frigate. Пока этого не сделано, **детекция не работает**, и `/status` об этом говорит.

## Почему не сделать проще

Напрашивается: пусть `/test` сама поднимает probe и правит конфиг NVR. Отказался сознательно.

Правка чужого `config.yml` из бота требует доступа к файловой системе NVR, которого у нас нет и быть не должно — креды Frigate живут только в адаптере, и ходить дальше API он не умеет. А главное: переключение детектора **выключает охрану**, и такое действие должно быть явным, руками, с осознанием последствий.

## Что `/test` проверяет и чего не проверяет

**Проверяет:** probe → детектор Frigate → трекер → запись клипа → MQTT → адаптер → `spotter.event` → домен → бот → сообщение.

**Не проверяет:** настоящую детекцию (она на это время выключена) и работу камер как источника — probe отвечает независимо от того, что в кадре.

# Что появилось за эту работу

| Что | Где | Зачем |
|---|---|---|
| `spotter-probe` | [`apps/probe`](../apps/probe/AGENTS.md) | фиктивный детектор на Rust, образ 12.5 МБ |
| Стенд с NVR | [`.e2e/nvr/`](../.e2e/nvr/README.md) | настоящий Frigate, девять проверок |
| `/test` | `apps/telegram` | одна команда вместо `test_delivery` + `test_media` |
| Сторож тишины | [`docs/source-watchdog.md`](source-watchdog.md) | тревога, когда NVR перестал говорить |
| Профиль `probe` | `production.probe.yml` | probe на живом узле, выключен по умолчанию |

Удалено: `spotter.event.test_seed`, `eventTestController`, `eventTestAction`, `/test_delivery`, `/test_media`.

## Что осталось непокрытым

**Доставка до конкретного получателя.** Стенд проверяет, что бот жив, получает каталог и не ходит в настоящий Telegram, но не утверждает «событие → сообщение в чат N»: регистрация получателя идёт через подписанный токен и живой чат.

**Тестовая инфраструктура Telegram.** `TELEGRAM_TEST_ENVIRONMENT=true` в конфиге есть, включается одним флагом, но не проверена — нужен отдельный токен от BotFather.
