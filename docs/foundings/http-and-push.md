# HTTP и push: наблюдения

## HTTP/1.0 оставляет `request.url` относительным

Голый прокси и некоторые пробы ходят по HTTP/1.0. В этом случае `request.url` относительный, статический обработчик на нём падал, и сервер отвечал 500 — на каждую загрузку страницы за таким прокси. Случай воспроизведён в тесте `createServer.test.ts`.

## `<img>` и `<video>` не умеют слать заголовки

Браузерные элементы не могут нести `Authorization`, поэтому медиа-маршруты были бы недостижимы именно для тех элементов, которым они нужны. Отсюда токен в query — это тот же грант, и он не покидает origin приложения, в отличие от пресайн-ссылки на S3, которая отдаёт сам объект.

## Push-сервисы схлопывают уведомления по `topic`

Поле `topic` (≤32 символов) заставляет push-сервис заменить недоставленное уведомление с тем же значением, а не ставить новое в очередь. Используется код события, чтобы всплеск обновлений схлопнулся в один сигнал. Мёртвые endpoint'ы (404/410) удаляются.

Результат таймлапса намеренно мимо коалесцирования: это единичный осознанный запрос, его нельзя схлопывать вместе со всплеском событий на камере.

## Пресайн-ссылка на S3 не годится для браузера

Пресайн-URL кросс-доменный, а объектные хранилища часто отвечают на preflight браузера вообще без заголовков `Access-Control-*`. В результате `<img>` не показывает ничего, а `<video>`, которому нужны Range-запросы, падает совсем.

Со стороны Telegram это невидимо: там ту же ссылку скачивают серверы Telegram, а не браузер. Поэтому PWA проксирует медиа через себя — заодно credentials хранилища и структура бакета не уезжают в браузер, а доступ идёт через авторизацию самого приложения.

## Telegram Bot API: media в текстовое сообщение

С версии 7.11 `editMessageMedia` позволяет добавить медиа к текстовому сообщению и заменить photo → video. На этом построено дописывание транскодированного видео в уже отправленное уведомление.

## Telegram Bot API: лимиты размера медиа

Скачивая медиа по URL сам, Telegram берёт не больше 5 МБ для фото и 20 МБ для остального. Сверх этого приходит `400: failed to get HTTP URL content` — та же ошибка, что и при недоступной ссылке, поэтому по тексту причину не отличить. Загрузка байтами поднимает потолок до 50 МБ, но не дальше. Клип больше лимита доставим только частями.

Размер presigned-ссылки узнаётся GET-запросом с `Range: bytes=0-0`, а не HEAD: подпись привязана к методу, и HEAD по GET-ссылке хранилище вправе отвергнуть.

Резка копированием потока возможна только по ключевым кадрам. Если один интервал между ними больше лимита, часть выйдет больше лимита — это исправило бы только перекодирование.
