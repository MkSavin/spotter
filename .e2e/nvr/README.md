# Стенд с настоящим NVR

> Общая картина всех уровней проверки — в [docs/testing.md](../../docs/testing.md).

Настоящий Frigate, настоящий брокер, и наш probe вместо детектора. Покрывает участок, который не покрывает больше ничто: **NVR сам порождает событие и сам публикует его в MQTT**.

Отдельно от smoke намеренно. Smoke отвечает на вопрос «поднимается ли развёртывание» с заглушкой вместо NVR и остаётся лёгким; этот стенд отвечает на вопрос «доходит ли до нас событие, которое родил сам NVR», и платит за ответ образом в ~500 МБ.

## Запуск

```sh
bun run nvr:source     # синтетическое видео, один раз; ffmpeg берётся из контейнера
bun run nvr:build      # образ адаптера, после правок в apps/frigate
bun run test:nvr
```

Без docker или без образа тест **пропускается** с сообщением, чего не хватает, — на чужой машине он не падает.

Руками:

```sh
docker compose -f .e2e/nvr/nvr.yml up -d --wait
curl -X POST localhost:8081/detect -d '{"class_id":0,"score":0.9,"frames":60}'
docker compose -f .e2e/nvr/nvr.yml exec mosquitto mosquitto_sub -t 'frigate/#' -v
```

Веб-интерфейс Frigate — `localhost:5050`, `/health` probe — `localhost:8081`, записанные вызовы бота — `localhost:8090/__calls`.

## Telegram

`spotter-telegram` поднимается с `TELEGRAM_API_ROOT=http://botapi:8090`, и grammY шлёт туда **каждый** вызов. Токен в стенде синтаксически валидный, но никуда не ведёт: дойти до реального чата прогон не может физически.

Заглушка умеет и обратное — **подсунуть боту сообщение**, как будто его написал человек:

```sh
curl -s -X POST localhost:8090/__send \
  -d '{"text":"/login КОД","chatId":777001}'
```

Без этого `/login` не проверить: получателя нет, пока кто-то не погасит код из настоящего чата, а без получателя событию некуда доехать.

`botapi` отвечает `ok` на всё и **запоминает**, что бот пытался отправить:

```sh
curl -s localhost:8090/__calls | python3 -m json.tool
curl -s 'localhost:8090/__calls?method=sendPhoto'
curl -s -X POST localhost:8090/__reset
```

`apiRoot` — не ручка ради теста: то же самое нужно для self-hosted Bot API server и для тестовой инфраструктуры Telegram (`TELEGRAM_TEST_ENVIRONMENT=true` — отдельные аккаунты, отдельный BotFather). В стенде включён только первый путь; второй требует настоящего токена.

## Из чего состоит

| Сервис | Роль |
|---|---|
| `frigate` | настоящий NVR, **версия закреплена** на `0.17.2` |
| `probe` | наш фиктивный детектор, [`apps/probe`](../../apps/probe/AGENTS.md) |
| `mosquitto` | брокер, тот же образ, что в проде |
| `spotter-frigate` | наш адаптер, настоящий образ |
| `spotter-server` | домен |
| `spotter-telegram` | бот, направленный на `botapi` |
| `spotter-pwa` | веб-приложение; объявляет свой адрес в heartbeat |
| `botapi` | пишущая заглушка Bot API — что бот **пытался** отправить |
| `redis` | шина, куда адаптер кладёт `spotter.event` |
| `minio` | S3, без него адаптер не стартует |

Версия Frigate закреплена не из осторожности: протокол детектора — интерфейс плагина, а не эндпоинт, но и он не вечен. Поднимать тег — отдельное решение с прогоном стенда за ним.

## Источник видео

`source.sh` собирает 30-секундный `testsrc` через контейнер с ffmpeg — на машину ничего не ставится. go2rtc крутит его по кругу и отдаёт как RTSP, так что Frigate видит стабильный поток и пишет записи.

Пиксели не важны: что «видно» в кадре, решает probe. Важно только, чтобы поток был валидным и непрерывным.

Каталог `media/` в `.gitignore` — там и сгенерированное видео, и записи Frigate поверх него.

Файл длиной 20 минут не случайность: `#loop` у go2rtc заканчивается на EOF, а флаги через `#input=` уезжают в конец команды, после выходного URL, где ffmpeg их отвергает. Файл длиннее любого прогона снимает вопрос целиком, а `testsrc` сжимается почти в ничто — 7 МБ.

## Грабли, на которые уже наступили

Все три выглядят одинаково — «probe не вызывают» — и лечатся в конфиге, а не в коде.

**`detect.enabled` в 0.17 по умолчанию `false`.** Камера захватывает поток, счётчики бодрые, `detection_enabled: False` — и ни одного запроса к детектору.

**Невалидный конфиг роняет Frigate в safe mode, а не в отказ.** Он поднимается, отвечает по HTTP и берёт **CPU-детектор вместо нашего**. Выглядит как исправный NVR, который просто не зовёт probe. Проверять до запуска:

```sh
docker run --rm -v "$PWD/.e2e/nvr/frigate.yml":/config/config.yml:ro \
  --entrypoint python3 ghcr.io/blakeblackshear/frigate:0.17.2 \
  -m frigate --validate-config
```

**Комментарии внутри `go2rtc.streams` ломают поток.** Frigate копирует этот блок в конфиг go2rtc дословно, вместе с комментариями, и комментарий между ключом и списком оставляет поток зарегистрированным без работающего продюсера: Frigate получает 404 от собственного рестрима.

## Что стенд проверяет

Одиннадцать проверок, ~250 секунд с холодного старта:

1. Frigate подключился к брокеру
2. Frigate опрашивает probe (значит детектор действительно наш)
3. Вооружённая детекция уходит в `frigate/events` настоящим payload
4. Адаптер кладёт её в `spotter.event` со `score`, дошедшим без изменений
5. Запрос по шине (`spotter.probe.request.frigate`) доходит до probe — путь команды `/test`
6. **Обрыв связи NVR ↔ брокер замечен**: сеть режется на живом стенде, `lastContactAt` замирает, а heartbeat продолжает идти
7. Frigate записал событие в свою базу
8. Бот работает против заглушки Bot API и не может достучаться до Telegram
9. Каталог доехал от домена до бота
10. PWA объявляет свой адрес — из него `/user_sign` строит ссылку на вход
11. **Событие доехало до зарегистрированного получателя**: код выпущен доменом, погашен через `/login` как настоящим человеком, и сообщение ушло в его чат

Шестая — воспроизведение сентябрьского сбоя. Сама тревога срабатывает через 15 минут, что для стенда слишком долго; проверяется, что **вход для сторожа настоящий и замирает вместе со связью**, а решение покрыто unit-тестами `SourceWatcher`.

## Что проверено вживую

Frigate 0.17.2 подключился к probe (`Model probe.model is ready` — файл модели не нужен), опросил его больше тысячи раз, и по команде `/detect` **сам породил события**: записи `person` на камере `front` с настоящими id и payload со структурой `before`/`after`, `score` и `max_severity: "alert"`.

Дальше их подобрал наш адаптер и положил в `spotter.event`:

```json
{"id":"1788454070.21682-sk0354","camera":"front","label":"person",
 "score":0.93,"type":"start","source":"frigate"}
```

`score: 0.93` — ровно то, что передали в `/detect`. Значение прошло probe → детектор → трекер Frigate → MQTT → адаптер → Redis, не изменившись. Именно этот путь подменяет вброс в `test_seed`.
