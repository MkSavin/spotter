# e2e

Сквозные тесты: настоящий Redis в Docker, настоящие контроллеры сервисов, обе топологии деплоя.

```bash
bun run test:e2e            # весь набор
bun test ./.e2e/delivery.test.ts
E2E_VERBOSE=1 bun test ./.e2e/...   # с логами сервисов
```

Без Docker набор **пропускается**, а не падает: `bun test` в CI и на машине без демона остаётся зелёным.

## Что настоящее, а что подделано

Настоящие: Redis (Streams, consumer-группы, PEL), регуляторы, контроллеры сервисов, транскодинг, forwarder с его же картой стримов.

Подделаны только чужие системы — NVR, S3, Telegram Bot API, web-push. Их нельзя поднять в CI, а Telegram не должен получать сообщения из тестового прогона. `fakeS3` при этом **хранит байты**: depot читает staged-объект обратно, и write-only заглушка вешает любой медиа-тест.

## Топологии

`single` — один Redis. `split` — ingest и cloud на разных Redis, между ними forwarder. Второе важнее: стрим, забытый в `UP_STREAMS`/`downStreams`, просто никогда не доезжает, и на одном узле это не воспроизводится. Один и тот же набор проверок гоняется на обеих.

## Чего эти тесты не ловят

`index.ts` каждого сервиса заканчивается `process.exit`, поэтому запустить его внутри раннера нельзя — тесты собирают те же контроллеры, что и сервис, но не его процессную обвязку. Ошибки в Dockerfile, env и compose остаются за кадром; для них нужен smoke на реальном compose.

## Что этот набор уже поймал

`recovery.test.ts` написан под гипотезу «NOGROUP не обрабатывается» и почти сразу нашёл другое, хуже.

Если Redis теряется целиком (`docker rm -f` контейнера — то есть обычное обновление образа), **блокирующий `XREADGROUP`, начатый до смерти сервера, не завершается никогда**: ни резолва, ни реджекта. Цикл чтения висит на `await`, ошибки нет, ветка восстановления не срабатывает — сервис выглядит здоровым и не читает ничего. Healthcheck это не ловил: `PING` идёт по другому соединению.

Измерено на живом контейнере:

| сценарий | до правки | после |
|---|---|---|
| `FLUSHALL` (соединение живо) | восстанавливается | восстанавливается |
| контейнер уничтожен и поднят | **навсегда STUCK** | восстанавливается |
| in-flight чтение при смерти сервера | не завершилось за 20 с | завершается по дедлайну |

Починено дедлайном на чтение (`BLOCK` + запас): зависание превращается в ошибку, соединение пересоздаётся, дальше отрабатывает уже существующая ветка NOGROUP. В логе видна вся цепочка:

```
WARN  Read stalled — replacing the connection
WARN  Consumer group missing — recreating
```

Регрессия закрыта и юнит-тестом (`RedisRegulator stalled reads`), так что без Docker она тоже не проедет.
