# AGENTS.md — `spotter-probe`

Фиктивный детектор объектов, который **приводит в движение настоящий Frigate**. Единственный сервис в репозитории не на Bun — почему, ниже. Общие конвенции — в корневом [AGENTS.md](../../AGENTS.md).

## Зачем

У Frigate нет хука «создать событие», зато есть штатный плагин-детектор [`zmq_ipc`](https://github.com/blakeblackshear/frigate/blob/v0.17.2/frigate/detectors/plugins/zmq_ipc.py): он не считает сам, а спрашивает по сокету, что в кадре. Probe отвечает на этот вопрос по команде.

Мы подменяем **только зрение**. Всё дальше настоящее: Frigate ведёт трекинг, пишет запись, считает `severity` и публикует в MQTT сам.

Это важно потому, что `test_delivery` и `test_media` кладут событие сразу в `spotter.event.test_seed`, минуя MQTT. Участок между NVR и адаптером не проверяет ничто — и именно он молчал в проде двое суток.

## Протокол

```
Frigate  → [ header_json, tensor_bytes ]   кадр
probe    → 480 байт (20 × 6 × float32)     что «найдено»
```

Строка: `[class_id, score, y_min, x_min, y_max, x_max]`, координаты нормированы 0..1. Пустые строки — нули; Frigate читает весь массив всегда, поэтому ответ **всегда 480 байт**, короткий он отбрасывает как битый.

Перед инференсом Frigate шлёт handshake `{"model_request":true}` и не начнёт работу, пока не получит `{"model_available":true,"model_loaded":true}`. Модели у нас нет — мы её и не запускаем, — поэтому отвечаем «готова» всегда.

## Управление

```
POST /detect  {"class_id":0,"score":0.9,"frames":30,"box_":[y1,x1,y2,x2]}
POST /clear
GET  /health  → {"ok":true,"framesLeft":N,"framesServed":M}
```

`frames`, а не секунды: Frigate спрашивает раз на проанализированный кадр, и счётчик кадров переживает камеру с другим FPS. По умолчанию 30 — одного кадра Frigate не хватит, он отбросит его как шум.

Когда кадры кончились, probe снова отвечает пустотой — **именно так закрывается событие**: объект перестал появляться.

`framesServed` в `/health` доказывает, что NVR действительно опрашивает детектор, а не просто подключён.

## Почему Rust, а не Bun

`zeromq@6` под Bun 1.4 падает на `bind`:

```
panic(main thread): unsupported uv function: uv_async_init
```

Под Node тот же код работает ([пробел в поддержке libuv](https://github.com/oven-sh/bun/issues/18546)), но второй JS-рантайм рядом с Bun читается как «у нас две ноды», и однажды кто-то напишет на нём сервис. Бинарь в 10 МБ так не читается.

Для Rust нашлась **чистая реализация ZMQ без C-зависимости**, отсюда цифры: образ **9.65 МБ** против ~130 МБ на Node, бинарь 1.1 МБ, рантайм в образе не нужен вовсе.

**Ничего не ставится на машины.** Сборка целиком в Docker: ни `cargo`, ни `rustc` не появляются ни у разработчика, ни на VPS, ни на ingest.

## Разработка

Локального Rust не требуется:

```bash
cd apps/probe
docker run --rm -v "$PWD":/w -w /w rust:1-alpine sh -c \
  'apk add --no-cache musl-dev >/dev/null; cargo test --release'

docker build -t spotter-probe:dev .
docker run --rm -p 5555:5555 -p 8080:8080 spotter-probe:dev
```

## Опасность

**Probe подменяет детектор Frigate.** Пока он активен, боевая детекция не работает — NVR видит только то, что мы ему скажем.

Поэтому:

- в production compose он за профилем `probe` ([`production.probe.yml`](../../.deployment/compose/production.probe.yml)) и выключен по умолчанию;
- поднимается только флагом: `./spotter up --probe`, и этот выбор **не запоминается** в `SPOTTER_PROFILES` — в отличие от фронтендов. Забыть фронтенд досадно, забыть probe — оставить участок без наблюдения;
- CLI печатает предупреждение при каждом таком запуске;
- `PROBE_ENDPOINT` передаётся только вместе с флагом, поэтому адаптер забывает probe сразу, как профиль снят;
- пока endpoint задан, адаптер шлёт `probeActive` в heartbeat, и `/status` печатает **🚨 ДЕТЕКТОР ПОДМЕНЁН** выше всех бодрых цифр источника.

Последнее важнее, чем кажется: без этой строки админ прочитает «последнее событие минуту назад» как хорошую новость, хотя это событие мы сами и заказали.
