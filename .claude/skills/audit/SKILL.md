# Аудит кода — Spotter

Read-only аудит кодовой базы по принципиальному чек-листу. Цель — найти реальные
расхождения с архитектурой и конвенциями проекта, а не сгенерировать правдоподобный текст.

## Железные правила

1. **Никаких правок кода.** Аудит только читает и описывает. Edit/Write по исходникам —
   запрещены, кроме записи самого отчёта в `.audits/`. Исправляй код, только если
   пользователь явно попросил после аудита.
2. **Каждый пункт проверяется по факту.** Никакого нейро-слопа. Для любого вывода
   (✅ или ❌) под рукой должно быть доказательство: `file:line`, фрагмент кода, вывод
   команды. Не нашёл доказательства — пиши «не проверено», а не выдумывай вердикт.
3. **Принципы, а не копипаста.** В отчёте описывай нарушенный/соблюдённый принцип
   своими словами + ссылка на место. Не вставляй простыни исходников; 1–3 строки
   контекста максимум.
4. **Кратко и содержательно.** Каждый пункт — суть проблемы + где + как чинить (1–2 фразы).
5. **Выбирай русский.** Пиши отчет на русском языке.

## Процесс

### 1. Определить scope
По умолчанию — весь репозиторий. Если пользователь назвал сервис/пакет/диапазон коммитов
(`apps/server`, «изменения в этой ветке») — сузь scope до него и отметь это в шапке отчёта.

Полезный контекст перед стартом (не доверяй памяти, перепроверь):
- `git status` / `git diff --stat` — что менялось, если аудит по диффу.
- `AGENTS.md` корня и сервиса — текущие конвенции (могли измениться).
- `bun run typecheck:full` и `bun run test` — фактическое зелёное/красное состояние.

### 2. Пройти чек-лист
Иди по разделам ниже. Для каждого пункта **сначала собери доказательство командой/чтением**,
потом выноси вердикт. Если пункт неприменим к scope — помечай `n/a`, не раздувай отчёт.

Вердикты: ✅ соблюдено · ⚠️ частично / риск · ❌ нарушено · `n/a` неприменимо · `?` не проверено.

### 3. Определить номер отчёта
`N = (макс. существующий N в .audits/AUDIT_*.md) + 1`. Если файлов нет — `N = 1`.

```sh
ls .audits/AUDIT_*.md 2>/dev/null
```

### 4. Записать отчёт
В `.audits/AUDIT_<N>.md` (папка `.audits/` уже в `.gitignore`). Структура — в конце скилла.

## Чек-лист (принципиальный)

Группы заточены под Spotter: Bun-монорепо на Redis Streams, SQLite/Drizzle, S3,
разделение домен/фронтенд. Каждый пункт — это **принцип**; проверяй его соблюдение по коду.

### A. Архитектура и границы сервисов
- **A1. Связь только через шину.** Сервисы общаются через Redis Streams (MQTT на входе),
  без прямых импортов/вызовов между `apps/*`. *Проверка:* импорты одного `apps/X` из другого `apps/Y`.
  *Чинить:* вынести контракт в `@spotter/transport`, общаться сообщением.
- **A2. Изоляция кред NVR.** `frigate`/`jwt`/`clipUrl`/`cameraLabels` живут **только** в адаптере
  (`apps/frigate`). По шине ходят S3-ключи, не байты и не токены. *Проверка:* grep этих токенов в `server`/`telegram`/`depot`.
  *Чинить:* перенести резолвинг медиа/кред в адаптер, наружу отдавать только ключ S3.
- **A3. Домен ≠ фронтенд.** В `server` нет grammy/рендера/Telegram-стейта; в `telegram` нет
  доменной истины (роли/события как источник). Мутации домена из telegram — только через
  `command.request`. *Проверка:* grep `grammy`/`editMessageMedia` в server; прямые записи в доменные таблицы из telegram.
  *Чинить:* перенести через `spotter.command.*`.
- **A4. NVR-специфика за абстракцией.** Любая привязка к конкретному NVR — в `@spotter/sink`-адаптере,
  потребители работают через контракты `@spotter/transport`. *Чинить:* спрятать за порт `Source`/`MediaProvider`/`Catalog`.

### B. Контракты сообщений и схемы
- **B1. Единый источник схем.** Формы сообщений/топиков определены в `@spotter/transport`
  (`schema/`), а не продублированы в сервисах. *Проверка:* самописные интерфейсы payload вместо импорта из transport.
  *Чинить:* поднять тип в transport, импортировать.
- **B2. Имена стримов не хардкодятся врассыпную.** Топики — из общих констант/хелперов, не строковые
  литералы в десятке мест. *Чинить:* вынести в константу/билдер имени.
- **B3. Валидация на входе контроллера.** Контроллер парсит сырьё и делает ранний `return`/`throw`
  на мусоре (Frigate шлёт «грязные» события). *Проверка:* контроллеры без guard'ов на `bufferToJson`.
  *Чинить:* добавить ранний выход на невалидном payload.

### C. Надёжность доставки (Regulator / Streams)
- **C1. XACK после успеха.** Подтверждение — только после успешной обработки, чтобы упавшее
  сообщение осталось в PEL. *Проверка:* нет ручного раннего ack / «fire-and-forget» с потерей.
  *Чинить:* доверить ack регулятору, не ack-ать до завершения работы.
- **C2. Poison-message защита.** Превышение `REDIS_MAX_DELIVERIES` уводит запись в `<stream>.dead`.
  Не обходить этот механизм кастомным ретраем. *Чинить:* использовать DLQ регулятора, не самокат.
- **C3. Таймауты длинных операций.** `REDIS_RECLAIM_MIN_IDLE_MS` выше самой долгой операции
  (транскодинг), иначе reaper заберёт ещё живое сообщение → дубль. *Проверка:* сопоставить idle-порог с длительностью ffmpeg/sharp.
  *Чинить:* поднять idle-порог либо разбить операцию.
- **C4. Идемпотентность обработчиков.** Повторная доставка (reaper/reclaim) не должна ломать
  состояние (двойные сообщения в TG, дубли в БД). *Проверка:* есть ли естественный ключ/upsert.
  *Чинить:* upsert по `eventId`/составному ключу, дедуп перед побочным эффектом.

### D. Слой Controller → Action
- **D1. Контроллер без бизнес-логики.** Контроллер: парс → payload → вызов action → publish.
  Бизнес-правила — в чистом `*Action`. *Проверка:* ветвления/расчёты внутри `*Controller`.
  *Чинить:* выделить логику в action, контроллер оставить тонким.
- **D2. Action чистый и тестируемый.** Action работает на типизированном payload, побочки —
  через переданный контекст (producer/logger/db), а не глобали. *Чинить:* инжектить зависимости аргументом.

### E. Конфигурация и окружение
- **E1. `process.env` только в config.ts.** Бизнес-логика читает конфиг, не env напрямую.
  *Проверка:* `grep -rn "process.env" apps/*/src` вне `config.ts`. *Чинить:* поднять в `resolveConfig`, прокинуть в контекст.
- **E2. Fail-fast через requireConfig.** Один агрегирующий guard в конце `resolveConfig`, падает
  со списком ВСЕХ недостающих переменных. *Проверка:* россыпь `if (!x) throw`. *Чинить:* собрать в `requireConfig`.
- **E3. Слоёные .env синхронны.** Каждой реальной переменной соответствует `.env.*.example`;
  креды (`FRIGATE_*`) — только в своём тонком слое, не в общем `.env`. *Проверка:* diff ключей `.env.*` vs `.example`.
  *Чинить:* дописать пример / убрать креды из общего слоя.

### F. Данные (SQLite / Drizzle)
- **F1. Доступ только через repository.** Бизнес-логика/команды не дёргают drizzle напрямую.
  *Проверка:* импорт `drizzle`/таблиц вне `db/`. *Чинить:* добавить метод в repository.
- **F2. Миграции в актуальном состоянии.** После правок `schema.ts` есть сгенерированная миграция;
  `drizzle/` едет рядом с приложением (Dockerfile копирует). *Проверка:* diff schema vs последняя миграция, COPY в Dockerfile.
  *Чинить:* `bunx drizzle-kit generate`, проверить Dockerfile.
- **F3. Разделение БД соблюдено.** Доменные таблицы — в server, Telegram-локальные — в telegram,
  без перекрёстных записей. *Чинить:* перенести запись на владельца через command-RPC.
- **F4. Синхронность bun:sqlite учтена.** Репозиторий возвращает значения (не лишние промисы),
  без ложного параллелизма поверх синхронного API. *Чинить:* убрать искусственный async.

### G. Ошибки, логирование, наблюдаемость
- **G1. Ошибки не глотаются молча.** `catch` либо обрабатывает, либо логирует с контекстом, либо
  пробрасывает — не пустой. *Проверка:* пустые/`catch {}`-блоки. *Чинить:* залогировать через саб-логгер или пробросить.
- **G2. Логи через stenograph с контекстом.** Используется `defaultLogger.sub(...)`, а не голый
  `console.*`; уровни осмысленны. *Проверка:* `console.log` в проде. *Чинить:* заменить на контекстный логгер.
- **G3. Секреты не логируются.** Токены/JWT/presign-URL/ключи S3 не утекают в логи. *Чинить:* маскировать/убрать из лога.

### H. Качество, типобезопасность, стиль
- **H1. Типобезопасность.** Минимум `any`; там где `any` — оправдан (комментарий/граница).
  Нет `@ts-ignore` без причины. *Проверка:* `grep -rn "any\b\|@ts-ignore" apps/*/src`. *Чинить:* типизировать или сузить.
- **H2. Зелёное состояние.** `typecheck:full` и `test` проходят. *Проверка:* запусти их. *Чинить:* починить красное (с разрешения).
- **H3. Стиль Biome.** Одинарные кавычки, без `;`, 2 пробела; `bunx biome check` чисто.
  *Проверка:* `bunx biome check`. *Чинить:* `bunx biome check --write`.
- **H4. Комментарии по делу.** Комментарии объясняют «почему», не дублируют код; над функциями —
  компактный JSDoc. *Чинить:* убрать шум, добавить «почему» где нетривиально.
- **H5. Дублирование/мёртвый код.** Нет копипасты логики между сервисами (должна жить в `packages/*`)
  и неиспользуемых экспортов. *Чинить:* вынести общее в пакет, удалить мёртвое.

### I. Тесты
- **I1. Покрыты критичные ветки.** Парсинг «грязных» событий, ретраи, авторизация/роли, граничные
  случаи. *Проверка:* наличие `*.test.ts` рядом с критичной логикой. *Чинить:* дописать тест на ветку.
- **I2. Тесты изолированы.** FS-тесты — в уникальных temp-директориях; логи заглушены
  (`defaultLogger.disable()`); нет зависимости от внешних сервисов/порядка. *Чинить:* изолировать состояние.

### J. Безопасность и эксплуатация
- **J1. Авторизация на командах.** Доменные команды/RPC проверяют роль/доступ; нет «открытых»
  мутаций. *Проверка:* обработчики `command.request` без проверки роли. *Чинить:* добавить guard роли.
- **J2. Presign-URL короткоживущие.** `S3_PRESIGN_EXPIRY` разумен; ключи S3 не уходят клиенту как
  постоянные ссылки. *Чинить:* укоротить срок, пресайнить по требованию.
- **J3. Чистка ресурсов.** Temp-файлы (depot), соединения, подписки закрываются; нет утечек
  (`DIRECTORY_CLEANUP`). *Проверка:* парные create/cleanup. *Чинить:* добавить cleanup в finally/stop().
- **J4. Graceful shutdown.** `run()` возвращает `{stop()}`; на SIGTERM подписки/коннекты гасятся,
  in-flight не теряется молча. *Чинить:* повесить обработчик сигнала, дождаться завершения.

## Формат отчёта `.audits/AUDIT_<N>.md`

```markdown
# Аудит кода Spotter — AUDIT_<N>

- **Дата:** <YYYY-MM-DD>
- **Scope:** <весь репо | apps/server | дифф ветки X>
- **Коммит:** <git rev-parse --short HEAD>
- **Состояние:** typecheck <pass/fail> · tests <pass/fail> · biome <clean/issues>

## Сводная таблица

| ID | Принцип | Вердикт | Где (file:line) | Кратко |
|----|---------|---------|-----------------|--------|
| A1 | Связь только через шину | ✅ | — | прямых импортов нет |
| A2 | Изоляция кред NVR | ❌ | apps/server/src/... :42 | clipUrl утёк в домен |
| ... | | | | |

Итог: ✅ N · ⚠️ N · ❌ N · n/a N. (только проверенные пункты)

## Находки (по приоритету: ❌ → ⚠️)

### [A2] Изоляция кред NVR — ❌
**Где:** apps/server/src/...:42
**Суть:** <в чём нарушение принципа, 1–2 фразы с доказательством>.
**Как чинить:** <конкретный шаг, 1–2 фразы>.

<повтори для каждой ⚠️/❌; ✅ и n/a достаточно в таблице>

## Что проверить вручную / не покрыто
<пункты с вердиктом `?`, и за пределами автоматической проверки>
```

Приоритет в «Находках»: сначала `❌`, потом `⚠️`. Пункты `✅`/`n/a` детально не расписывай —
их место в таблице. В конце отчёта НЕ предлагай автоматически чинить: жди явной просьбы.
